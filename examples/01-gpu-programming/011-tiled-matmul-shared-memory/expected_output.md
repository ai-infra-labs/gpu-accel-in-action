| 观察 | 数据 | 说明 |
|---|---|---|
| 轮数 = `ceil(N/T)` | N=33 → 3 轮 | 33/16 = 2.06，必须 3 轮才覆盖最后 1 列 |
| `floor` 在整除时无法区分 | N=32、1024 两行两列误差相同 | 整除时 `ceil == floor`，选这些用例测不出 bug |
| `floor` 的误差随余数变化 | N=33 时 7.80e-02，N=31 时 5.53e-01 | 余数越小，漏掉的越少，误差越小——说明"看起来差不多"最危险 |
| 全 1 矩阵是确定性证据 | 33.0 vs 32.0 | 差值恰好是漏掉的那一列，不是浮点噪声 |

**这个脚本证明的是索引逻辑，不是 CUDA 行为**：它不复刻 GPU 的累加顺序，
也不验证 float32 舍入。

判读方式：

- 验收容差 `rtol=1e-3, atol=1e-3` 是本文的教学条件，不是通用 GEMM 标准。
- GFLOPS 用 `2 * N^3` 的工作量模型折算，只用于同输入、同精度、同口径下的对照。
- 20 次采样的 median/p95 只够看趋势，不足以支撑尾延迟结论。
- `naive vs tiled` 那一行是辅助诊断，不作为验收条件：两个 Kernel 的编译优化、
  FMA 生成路径可能不同，不必逐位一致。

## 4. 踩坑记录

待填（`tiled_matmul.py` 部分）。至少记录：

- 共享内存每块 `16×16×4 B × 2 = 2 KB`，看似不大，但它是占用率的分母；
  把 `TILE_SIZE` 提到 32 时，共享内存与寄存器会同时吃紧
- 两次 `__syncthreads()` 缺一不可：第一次保证数据搬完，第二次保证没人还在读
- 越界位置必须填 0 而不是跳过——跳过会让 `As/Bs` 保留上一轮的值，
  累加结果被污染，这种错误在小规模整除时完全看不出来
