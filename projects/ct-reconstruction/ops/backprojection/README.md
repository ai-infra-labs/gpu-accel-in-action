# backprojection —— CT 反投影（主线算子）

> 状态：**未实测**。本机（Apple Silicon）无 `nvcc`，代码未在 NVIDIA GPU 上编译运行过。
> 实测数据请填 [`../../docs/expected_output.md`](../../docs/expected_output.md)。

## 问题定义

CT 重建的分两步走：**滤波**把投影去模糊，**反投影**把一维投影「抹」回二维图像。
本篇只做反投影这一段——它是整条链路里访存最不讲道理的一步。

二维平行束的教学近似（不是生产级 FDK 锥束重建）：

```
体素 (ix, iy) → 物理坐标 (x, y)
角度 θ 下，该点的投影位置   p = x·cosθ + y·sinθ
换算成探测器索引           u = p / detSpacing + (nDet-1)/2
在 sinogram[a][·] 上双线性取样，全部角度累加，最后乘 dθ 归一化
```

```
vol[x][y] = dθ · Σ_a  bilinear( sinogram[a], u(x, y, a) )
```

一句话：**每个体素都要把每条投影回头看一遍**。数据量是 `nx·ny·nAngles` 个采样点，
其中 `sinogram` 被反复读、`vol` 只写一次——典型的「读远多于写」型 kernel。

## 线程映射

| 版本 | 线程映射 | 一个线程做什么 |
|---|---|---|
| `v0_naive.cu` | 一维摊平 `block(256)`，`idx % nx` 还原二维 | 一个体素，跑完 180 个角度 |
| `v1_optimized.cu` | 二维 `block(32,8)`，`threadIdx.x → 体素列` | 同上 |
| `v2_industrial.cu` | 同 v1 | 同上 |

三者**算法完全相同**，差别只在「同样的事怎么让它跑得快」：

- **v0**：每个体素每个角度都重算 `cosf/sinf`，每轮都重算 `a*nDet` 的偏移，
  取样用普通全局读取，二维索引靠整数除取模还原。它是基准，不是反面教材——
  没有它，后面两版的收益无从量化。
- **v1**：改线程映射，让一个 warp 的 32 个线程落在同一行相邻 32 列，
  探测器索引因此也相邻，同一角度的 32 次取样压成少量内存事务；
  顺手省掉整数除取模、把行首指针递进、用 `__ldg` 走只读缓存、
  把双线性从两乘两加改成 `s0 + (s1-s0)·f`。
- **v2**：把 `(cosθ/detSpacing, sinθ/detSpacing)` 预存进常量内存。
  每体素每角度的 2 次三角函数与 1 次除法直接消失；常量缓存对同 warp 同地址是广播语义。
  代价是常量内存有容量上限（这里卡在 1024 条角度），且几何一变就得重传——
  这是「预计算换容量」的典型权衡，不是无脑优化。

> 关于 `block(16,16)` 的说明：16×16 也是常见选择，但一个 warp 会被劈成两行各 16 列，
> 同一条投影行上只覆盖 16 个相邻探测器，访存连续性不如 32×8。这里用 32×8，
> 让 `threadIdx.x` 与探测器轴对齐。想验证的话，把 `dim3 block(32,8)` 改成 `(16,16)`
> 再跑一遍 `ncu`，看 Global Load Efficiency 的差别。

## 文件

| 文件 | 说明 |
|---|---|
| `v0_naive.cu` | 朴素版：体素驱动 + 每轮重算三角函数 + 普通全局读取 |
| `v1_optimized.cu` | 二维线程映射 + 指针递进 + `__ldg` + 少一次乘法 |
| `v2_industrial.cu` | 常量内存角度表 + `__launch_bounds__` + 角度循环部分展开 |
| `test.cu` | 以 v0 为 golden，逐元素 `|a-b|/(|b|+1e-12) < 1e-5` 判定 v1/v2 |

`test.cu` 用 `#define MI_NO_MAIN` 后 `#include` 三个 `.cu`，把三份实现编进同一个
翻译单元——校验的是真正要跑的那份 kernel，而不是抄出来的副本。共享的
`MiGeom` / `mi_build_sinogram` 因此用宏守卫，保证只定义一次。

## 运行

```bash
# 单文件直接编译，不需要 CMake、不需要额外头文件
nvcc -O3 -arch=native v0_naive.cu     -o v0_naive     && ./v0_naive
nvcc -O3 -arch=native v1_optimized.cu -o v1_optimized && ./v1_optimized
nvcc -O3 -arch=native v2_industrial.cu -o v2_industrial && ./v2_industrial

# 正确性校验（golden = v0）
nvcc -O3 -arch=native test.cu -o test && ./test
```

命令用 `-arch=native`（CUDA 11.5+，自动探测本机计算能力）。nvcc 更老时改显式
`-arch=sm_XY`；**不要写死 `-arch=sm_86`**——它只生成 8.6 的 SASS、不嵌 PTX，
换到 H100 / B200 / RTX 50 上会直接报 `no kernel image is available for execution`。

`test` 会以退出码 0/1 表示 PASS/FAIL，可以直接挂进 CI。

## 默认规模与调参

| 参数 | 默认值 | 说明 |
|---|---|---|
| `nx × ny` | 256 × 256 | 重建图像尺寸；调到 512×512，采样点数涨 4 倍 |
| `nDet` | 384 | 探测器像元数，约 `1.5 ×` 图像边长，保证物体不被切边 |
| `nAngles` | 180 | 180° 内均匀采样；`dTheta = π / nAngles` |

采样点总数 `256×256×180 ≈ 1.18e7`。这个规模在入门卡上跑几十毫秒，
足够让三个版本的差距显现，又不至于等太久。想压垮 L2、看「访存墙」的样子，
把 `nx/ny` 提到 512、`nAngles` 提到 360（采样点涨 8 倍）。

## 几何自检（NumPy 等价实现，**不是** GPU 实测）

在没有 N 卡的环境里，唯一能验证「映射方向对不对」的办法是把同一套公式用
NumPy 重写一遍，看重建图与 phantom 的结构是否对得上。这一步查的是**几何**，
不是性能，也不是 kernel 正确性。

64×64、96×64 规模下的结果：

| 检查项 | 值 | 说明 |
|---|---|---|
| phantom 均值 | 0.4198 | 椭圆叠加后的灰度均值 |
| 未滤波重建均值 | 2.7466 | **绝对值不可比**：未滤波反投影对低频过度加权，尺度没有标定意义，只看结构 |
| corr(phantom, 重建) | 0.8508 | 正相关且明显高于左右镜像（0.8353）与上下镜像（0.8364），说明 `p = x·cosθ + y·sinθ` 的方向没搞反 |
| 高通后 corr（未滤波） | 0.5349 | 抹掉低频后，未滤波重建的结构位置信息明显变弱 |
| 高通后 corr（滤波后） | 0.7494 | 加上 `ramp-filter` 的三抽头高通，结构相关性从 0.53 抬到 0.75——这就是「先滤波再反投影」在数值上的意义 |

镜像版本的相关性只低一点点，是因为未滤波反投影本身把结构抹得很开，正负样本差别被压小了；
所以判方向不能只看相关值大小，**要三种朝向一起比**，最高的那个才是对的。

## 已知限制（务必读）

1. **几何是教学近似**。真实 FDK 是锥束（cone-beam）重建，要处理射线源到旋转中心、
   探测器到旋转中心的距离、体素沿 z 轴的锥角放大；这里退化成二维平行束，
   只保留「体素驱动 + 投影寻址」这一层骨架。
2. **没有滤波**。反投影前不滤波，重建结果是模糊的（低频被过度加权）。
   本篇只优化反投影这一步，滤波在 [`../ramp-filter/`](../ramp-filter/) 里单独讲。
3. **sinogram 是解析生成的**。物体由若干椭圆叠加，椭圆在平行束下的线积分有闭式解，
   所以数据直接算出来，没有离散化噪声、也没有真实 CT 的量子噪声与散射。
   好处是三层版本的差异只可能来自 kernel 本身，不会和噪声混在一起。
4. **只支持 `nAngles ≤ 1024`（v2）**。超过这个数，常量内存表放不下，
   `mi_upload_angles_v2` 会直接报错退出，而不是静默降级——工业代码里
   「悄悄走慢路径」比「明确失败」更贵。
5. **测试容差 1e-5 不是 0**。v2 把除法换成乘倒数，末位必然有差异，
   属浮点结合律的正常误差；若哪天容差需要放宽到 1e-4，说明有人动了算法而不是改了写法。
